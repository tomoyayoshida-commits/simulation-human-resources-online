# 出力機能（機能16）設計書：保存してから出す

作成 2026-09-03。作業机（機能15）から出力を切り離し、
**「保存された配置案」を対象に CSV / 告知用PDF / エグゼクティブサマリPDF の3通りを出す**ための設計。

---

## 1. 結論

作業机の「CSV出力」ボタンを**「この案を保存」に置き換える**。保存すると Firestore に1件追記され、
そのまま出力ステップへ進む。**作業机の上では一切出力しない**。

| 決めたこと | 内容 |
| --- | --- |
| 保存先 | Firestore `/simulationRuns/{runId}`（`web-firebase-plan.md` で設計済み・Phase (d)の一部先行実装） |
| PDF生成 | 印刷CSS ＋ `window.print()`。PDFライブラリは入れない |
| 制約違反時 | **保存は可・出力は不可**。現行 §8-2 の門を出力側へ移す |

### 1.1 なぜ作業机から出力を外すのか

告知用PDFもエグゼクティブサマリも「**確定した配置についての文書**」である。
一方で作業机はドラッグのたびに状態が変わる下書き板であり、そこから直接文書が出せると
「どの時点の盤面を配ったのか」を誰も特定できない文書が量産される。
保存を挟むのはUIの整理ではなく、**配布する文書に版（runId）を与える**ための設計である。

### 1.2 既定路線との関係

新規の方針転換ではない。`workbench-plan.md` §8-4 で
「v1はCSV出力のみ。ただし将来の保存機能を見越した余裕のある作りにする」と判断済みで、
その拡張点（`WorkbenchExport` / `serializeWorkbenchState`）は実装済みのまま未使用で残っている。
本書はそこに実装を入れる。

## 4. 設計

### 4.1 遷移：出力は `#p4` のステップにせず、独立パネル `#p7` にする

当初案は `#p4-export-step`（第4ステップ）だったが、**§8-1 で一覧を作ると決めた時点で成立しなくなった**。
理由は入口が2つになるため：

- 作業机からの保存直後（`#p4` の文脈がある）
- `#p0` の一覧から後日開く（`#p4` の取込データが無い。`state.employees100` は空）

出力を `#p4` のステップにすると、後者の経路でパンくずが「データ取込 ▸ 配置比較 ▸ …」と
存在しないステップを指し、`#p4-import-step` へ戻るリンクが壊れる。
**出力画面が要るのは保存済みドキュメント（roster も params も自身が持つ）だけ**なので、
`#p4` に依存させる理由がそもそも無い。

```
#p0 ─┬─▶ #p4（配置比較）… 取込 → 4課題比較 → 作業机 ─[保存]─┐
     │                                                      │
     └─▶ #p7（保存した配置案）… 一覧 ◀───────────────────────┘
                                  │
                                  └─▶ 出力（① CSV ／ ② 告知用 ／ ③ サマリ）
```

- `#p7` は `#p7-list-step`（一覧）と `#p7-export-step`（出力）の2ステップ
- 作業机で保存すると `#p7` の出力ステップへ直行する。**保存に成功してからしか出力画面に入れない**
- どちらの経路でも出力画面は同じ `SavedRun` 1件だけを見る。パンくずは
  「トップ ▸ 保存した配置案 ▸ 出力」で一本化される
- 作業机へ戻って直した場合は**別の runId として保存し直す**（追記のみ原則。同じ案を上書きしない）

`renderer.ts` の `Step` 型に `'list' | 'export'` を足し、`showStep` / `currentStep` / `renderBreadcrumb`
を `#p7` に対応させる。`#p4`・`#p5` には該当要素が無いので `toggleAttribute` は何もしない
（`#p5` に `bench-step` が無いのと同じ扱い）。

### 4.2 保存するドキュメント

```
/simulationRuns/{runId}
{
  task, metric,                    // WorkbenchExport
  assignment: {社員番号: 'A'|'B'|'C'},
  params,                          // オプション値を変えられるので再現に要る
  roster: Employee[],              // §4.2.1
  title,                           // 既定「課題N 配置案 YYYY-MM-DD」
  savedBy,                         // メールアドレス
  savedAt,                         // serverTimestamp()
  feasible, companyRevenue, companyProfit, movedFromBaseline   // 一覧表示用の非正規化
}
```

`runId` は Firestore の自動IDとする（時刻由来のIDにすると同時保存で衝突しうる）。

#### 4.2.1 roster を埋め込む（`/datasets` を切らない）

`web-firebase-plan.md` は `/datasets` に `Employee[]` を置き `simulationRuns` から参照する形を想定しているが、
**v1 では `simulationRuns` に直接埋め込む**。理由は3つ：

- 出力の再現には roster と params が必ず要る。参照にすると「片方だけ消えた」状態を扱う必要が出る
- 実データ（`資料/human_resources_100.csv`・100名）で実測 **roster 6,865 バイト＋assignment 1,101 バイト**。
  Firestore の1ドキュメント上限 1MB に対し 1% 未満で、500名版でも 35KB 程度に収まる
- `/datasets` を切ると取込フローにも手を入れることになり、この機能の範囲を超える

代償は同じ名簿が run のたびに複製されること。名簿を横断で扱いたくなった時点で `/datasets` へ正規化する。

#### 4.2.2 保存されないもの

`history`（undo履歴）と `baseline` は保存しない。前者は作業中の一時情報、後者は
`task`・`metric`・`roster`・`params` から再計算できる（`optimizer` を再実行すれば同じ解が出る＝決定性が保証されている）。

### 4.3 3つの出力に載せる項目

**出力画面は1つでも、項目は共通化しない。**とくに②に人件費が載ると事故になる。

| | ① データCSV | ② 告知用PDF | ③ サマリPDF |
| --- | --- | --- | --- |
| 目的 | 再取込・二次加工 | 全社員へ配る名簿 | 経営層への報告 |
| 読む人 | 担当者 | 全社員 | 役員 |
| 氏名 | ✕ | **○** | ✕ |
| 顔写真 | ✕ | ✕（§4.3.2） | ✕ |
| 社員番号 | ○ | ○ | ✕ |
| 配置先事業部 | ○ | ○ | 人数のみ |
| 異動の旧→新 | ✕ | ✕（§4.3.1） | 人数のみ |
| 能力値4項目 | ○ | **✕** | ✕ |
| **人件費** | ○ | **✕（厳禁）** | 全社合計のみ |
| 貢献度・タイプ | ○ | ✕ | ✕ |
| 全社売上・利益 | ✕ | ✕ | ○ |
| 事業部別の充足率 | ✕ | ✕ | ○ |
| 判断文 | ✕ | ✕ | ○（`generateReasonText`） |

- ① は `buildAssignmentCsv` を**無変更で**呼ぶ。ファイル名だけ `配置案_課題N_YYYY-MM-DD.csv` に変える
- ② は**全100名の新体制表**（§8-2）。**社員番号・氏名・配属先の3列**の名簿表。
  事業部ごとに区切り行を挟み、区切りの中は社員番号順（§4.3.2）。
  プロフィール未登録者は氏名欄が「（氏名未登録）」になるだけで行は落ちないこと（`profile-plan.md` 受入基準2 と同じ扱い）

#### 4.3.1 ②に「旧所属」を併記しない（当初案からの変更・実装時に判明）

当初は異動者に「← 営業部」と旧所属を併記する想定だったが、**採らない**。

本アプリの「異動」は `diffAssignment(baseline.assignment, assignment)` ＝
**最適解から人手で動かした差分**であって、社員の現在の実所属からの差分ではない。
取込CSVに現所属の列が無い以上、アプリは実所属を知らない。
これを全社員向けの文書に「異動」と書いて出すと、社内では違う意味に読まれる数字が独り歩きする。

最適解からの差分は**経営層向けの③にだけ**「最適解からの調整 N名」として載せる。
あちらは判断の記録なので、この意味で正しく読まれる。

将来、取込CSVに現所属列を足して実所属を持つようになったら、そのとき②に旧→新を入れる。
- ③ は A4 縦1枚に収める。`mockup-exec-summary.html` の体裁を移植する

#### 4.3.2 ②は顔写真カードではなく名簿表にする（ユーザー判断・2026-09-03）

当初の実装は事業部ごとに章立てし、顔写真＋氏名のカードを4列グリッドで並べる形だった。
これを**社員番号・氏名・配属先の3列の表**に変える。掲示・回覧される事務文書としては、
写真の一覧より「自分の行を探して配属先を読む」ほうが本来の用途に近い。

| | 変更前 | 変更後 |
| --- | --- | --- |
| 並び | 事業部ごとの章 → 章内で社員番号順 | 表1つ＋事業部の区切り行 → 区切り内は社員番号順 |
| 1名の表現 | 顔写真＋氏名＋社員番号のカード | 社員番号／氏名／配属先の1行 |
| 事業部 | 章見出し | 区切り行＋各行の「配属先」列 |
| 事業部別人数 | 章見出しの脇 | 表の前の要約（3事業部を横並び）と区切り行 |
| 氏名未登録 | 社員番号を名前の位置に出す | 氏名欄が「（氏名未登録）」（社員番号は別列にある） |

事業部の区切りは**表を3つに割らず、1つの表に区切り行（`colspan=3`）を挟む**形にする。
列幅と見出し行を全事業部で共通にしておくため。
区切りがあっても「配属先」列は各行に残す。改ページが区切りの途中に落ちたとき、
区切り行の見えないページでも1行だけで配属先が読めるようにするため。
事業部色は区切り行と「配属先」セルの `border-left` で出す（§4.4 のとおり背景色には頼らない）。

`AnnouncementMember` から `photo` を落とす。この型が §4.3 の「載せない項目」の関門なので、
写真を出さない判断は文言ではなく**型から消す**ことで担保する（能力値・人件費と同じ扱い）。

### 4.4 印刷の実装

- ②③はそれぞれ専用のDOMを `#p4-export-step` 内に**隠しては置かない**。
  「② を印刷」を押した時点でそのHTMLを生成して `body` 直下に差し込み、`window.print()`、
  `afterprint` で除去する。常時DOMに置くと `#wb-root` の再描画コストと混ざる
- `@media print` で `.topbar` / `.breadcrumb` / `.btn` / 出力ステップのUIを `display:none`、
  対象の1枚だけを出す。`@page { size: A4 portrait; margin: 14mm; }`
- ②に画像は出さない（§4.3.2）ので、印刷時の追加読み込みは発生しない。
  ただし**ブラウザ既定で背景色・背景画像は印刷されない**ため、
  事業部色は `border-left` など前景で表現し、`print-color-adjust: exact` に依存しない

### 4.5 制約違反の門をどこに置くか

現行 §8-2 は「違反があるとCSV出力させない」。これを**出力側へ移す**（ユーザー判断・2026-09-03）。

| 操作 | 違反あり | 挙動 |
| --- | --- | --- |
| 保存 | 許す | 下書きとして保存。`feasible: false` で記録し、一覧・出力画面で明示 |
| ①②③の出力 | **禁じる** | ボタンを `disabled`、理由をツールチップに出す（現行の文言を流用） |

保存を許すのは、作業を中断して別の日に続けられるようにするため。
出力を禁じるのは §8-2 の「違反したものを外に出さない」という判断がそのまま生きているため。

| ファイル | 責務 | テスト |
| --- | --- | --- |
| `src/renderer/runStore.ts` | `/simulationRuns` の I/O。`profileStore.ts` と同じ形 | ✕（Firestore依存） |
| `src/renderer/exportDocs.ts` | ②③のHTML生成。**純粋関数・DOM非依存** | **○** |

### 4.7 Security Rules

`web-firebase-plan.md` の「追記のみ・更新削除不可」をそのまま実装する。

```
match /simulationRuns/{runId} {
  allow read:   if isMember();
  allow create: if isMember() && request.resource.data.savedBy == request.auth.token.email;
  allow update, delete: if false;   // 履歴の完全性
}
```

`/employees` が更新削除を許しているのは「マスタだから」という明示的な例外であり（`firestore.rules:12`）、
`simulationRuns` は履歴なので原則どおり閉じる。

### 4.8 保存時の命名（§8-3）

「この案を保存」を押すと、その場に名前の入力欄が開く（別ダイアログにしない）。

- 既定値は `課題N 配置案 YYYY-MM-DD`。そのまま「保存する」を押せば既定名で保存される
- 空欄のまま保存しようとしたら既定値に戻す（無題のドキュメントを作らない）
- 入力欄の開閉は `WorkbenchViewData.savingTitle`（`string | null`）で表し、
  **HTML生成は純粋関数のまま**にする。`null` なら閉じている
- 保存中は `loading.ts` のオーバーレイを使い、二重送信を防ぐ

## 6. 受入基準

1. 作業机に出力ボタンが無く、「この案を保存」だけがある
2. 保存すると `/simulationRuns` に1件増え、出力ステップへ遷移する
3. 制約違反のある案も保存できる。ただし①②③のボタンは `disabled` で理由が出る
4. ①のCSVが現行と同一内容（`buildAssignmentCsv` 無変更＝退行なし）
5. **②に人件費・能力値・貢献度が一切現れない**（テストで固定）
6. ②でプロフィール未登録の社員が居てもレイアウトが崩れない
7. ③がA4縦1枚に収まる
8. 保存済みドキュメントを更新・削除しようとすると Rules に拒否される

## 7. やってはいけないこと

- PDFライブラリを入れること（§2.5 で判断済み）
- 保存前の作業机の状態から直接出力できる裏口を残すこと

### 8-1. 保存済み案の一覧・再出力の導線 → **`#p0` に一覧を追加する**

`#p6`（人材プロフィール）と同じく、主動線の2カードを薄めない小さなリンクとして置く。

URLハッシュでの共有（候補b）は採らない。閲覧には認証が要るため
リンクだけでは開けず、「一覧から探す」で用は足りる。

### 8-2. ②告知用PDFに載せる範囲 → **全100名の新体制表**

異動者だけの通知ではなく、全社員の新しい配属を並べた一覧とする。**異動しない人も載せる**（§4.3）。
旧所属の併記は採らず（§4.3.1）、体裁は顔写真カードではなく名簿表とした（§4.3.2）。
事業部の区切りは章立てではなく、1つの表に挟む区切り行として残す。

### 8-3. `title` を利用者に入力させるか → **保存時に命名させる**

「更新削除不可」の原則により後から改名できないため、保存の瞬間に名前を確定させる。
既定値を入れた入力欄を出し、そのままでも保存できるようにする（§4.8）。
