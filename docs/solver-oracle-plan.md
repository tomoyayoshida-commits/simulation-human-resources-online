# 数理最適化ソルバ導入方針（Sonnet向け作業指示）

> **アルゴリズム／依存関係の変更（CLAUDE.md §9で事前確認必須）**なので、実装前の合意用として書く。
> 本書は調査済みの事実を含む。**§2 の内容は再調査しないこと**（実測とコード確認で確定済み）。

## 1. 結論

**本番コード（`src/`）にソルバは入れない。テスト専用の検証オラクルとして `highs`（HiGHSのWASM版）を devDependency に入れる。**

導入の動機は「課題2（A事業部利益最大化）が正しく実装されていないかもしれない」だったが、調査の結果**課題2は現行実装で正しく、かつ最適**だった（§2.2）。したがって「答えを直す手段」としてのソルバは不要。

一方で、**最適化の中核である `assignment.ts`（自前MCMF・149行）を守っているテストが5名×3事業部の1件しかない**ことが判明した（§2.3）。ここを独立実装で検証することが、いま最も費用対効果が高い。それが本書のスコープ。

## 2. 調査済みの事実（再調査不要）

### 2.2 課題2は正しく、かつ最適だった

検証方法と結果：

- 861候補すべてを**枝刈りなしで**MCMFで解き、実行可能な中の最良A利益を求めた → **19.44**。`runOptimization(employees, 2)` の答えと一致。**枝刈りは最適解を落としていない。**
- 現行の答え：配分 `A:47 B:41 C:12`、A利益 19.44、全社売上 59.74。
  A:47 は充足率 1.175 で過剰ペナルティの崖（1.20）の直前。1人追加あたり売上寄与 約0.36億 > コスト 約0.20億 なので、崖まで詰めるのが正しい挙動。**数値は妥当。**
- 構造的な穴は1つある：**内側のMCMFは「全社売上>58億」を制約として持たない**。ある人数配分でMCMF最適解が infeasible になると、その配分内に「A利益はやや劣るが実行可能」な解があっても丸ごと捨てられる（`optimizer.ts:209` の `if (!result.feasible) continue`）。
  → ただし実データでは**容疑候補0件**。さらに能力値を一律縮小して制約を binding にした条件（全社売上58.07のギリギリ）でも**0件**だった。**実害は確認できていない潜在バグ**。優先度は低い（対応するなら §5 Phase 3）。

### 2.3 MCMFを守っているテストが1件しかない ← これが本題

`test/optimizer.test.ts` の `bruteForceOptimize` は、`buildValues` 相当を再実装しているが**内部で `solveAssignment` を呼んでいる**（`optimizer.test.ts:61`）。
したがって 15.5秒かかっている `枝刈り…完全一致` テストは、**枝刈りロジックしか検証していない**。MCMFが間違っていれば新旧そろって同じ間違いをするため、素通りする。

`assignment.ts` を直接検証しているのは `solveAssignment: 全探索(5名×3事業部)の最適値と一致`（`optimizer.test.ts:114`）**の1件のみ**。5名・`{A:2,B:2,C:1}`・乱数値という規模。

`assignment.ts` は Johnson ポテンシャル＋Bellman-Ford初期化＋Dijkstra の自前実装で、しかも被約コストの負値を0にクランプするFP対策（`assignment.ts:93`）を含む。**この規模のテストで守るには実装が重すぎる。**

特に危険なのは値のスケール。`buildValues` は `primary * 1e6 + secondary`（`optimizer.ts:86`）を作るため、実際にMCMFへ渡る値は**約1e7のオーダーで、意味のある差は1e0のオーダー**。7桁の動的レンジがポテンシャル計算とクランプに乗る。既存テストの `rnd()*100` はこのスケールを一切踏んでいない。

## 5. 実装手順

### Phase 0：導入と疎通（ゲート：既存テストが全通過）

1. `npm i -D highs`
2. `test/helpers/lpOracle.ts` を新規作成。HiGHSの初期化（WASM読み込みは非同期）をモジュールスコープで1回だけ行い、使い回すこと。**テストごとに初期化しない**（遅い）。
3. 疎通確認用に自明なLP（例：`max x, s.t. x<=3`）を1本解いて `3` が返ることだけ確認する捨てテストを書き、通ったら消す。
4. `npm test` が全通過することを確認。

### Phase 1：`solveAssignment` の独立検証（本命）

`test/assignment.oracle.test.ts` を新規作成する。

**検証する契約**：`solveAssignment(employees, values, counts)` は、`Σ_i values[i][assigned(i)]` を最大化し、各事業部の人数をちょうど `counts[u]` にする。

**定式化（輸送問題／LP）**：

```
変数  x[i][u] ∈ [0,1]        i = 0..n-1, u ∈ {A,B,C}
目的  maximize Σ_i Σ_u values[i][u] · x[i][u]
制約  Σ_u x[i][u] = 1              各 i について（1人は1事業部）
      Σ_i x[i][u] = counts[u]      各 u について（定員ちょうど）
```

制約行列は完全単模（bipartite transportation）なので**LPの頂点解は自動的に整数**になる。ただし内点法だと分数解が返りうるため、**変数を整数型（0/1）として宣言してMILPとして解くこと**。HiGHSならこの規模は一瞬で解ける。

**比較の仕方**：

- **目的関数値で比較する。割当そのものを比較してはいけない。** 同値解が複数あるのが普通で、MCMFとHiGHSでどちらを返すかは一致しない。
- 許容誤差は**相対**で取る。値のスケールが1e7なので絶対誤差1e-9では落ちる。`Math.abs(a-b) <= 1e-9 * Math.max(1, Math.abs(a), Math.abs(b))` 程度。
- 人数制約 `counts` の充足は別途 assert する。

**テストケース（全部入れる）**：

| # | 内容 | 狙い |
|---|---|---|
| 1 | 100名・実データ由来の `values`・`enumerateHeadcounts(100)` から数点サンプル | 実運用スケール |
| 2 | **`primary*1e6 + secondary` と同じスケールの値**（§2.3の理由） | ポテンシャル計算とFPクランプの検証。**最重要** |
| 3 | 同値が多数（`values` を少数の離散値から生成） | タイブレークで増加路が循環しないか |
| 4 | 負値を含む（課題2の `profitValue` は負になりうる） | Bellman-Ford初期化の検証 |
| 5 | 全値が同一 | 退化ケース |
| 6 | `counts` が極端（`{A:80,B:10,C:10}` など最低人数境界） | 容量制約の端 |
| 7 | 110名（採用後） | サイズ変化 |

乱数は既存の `makeRng(seed)` 方式を踏襲し、シードを固定して決定的にすること。

**ゲート**：全ケースで目的関数値が一致すること。**一致しなかった場合は `assignment.ts` を直す前に必ず報告する**（CLAUDE.md §9）。不一致は仕様解釈ではなく実装バグの可能性が高いが、オラクル側の定式化ミスの可能性も同程度にある。両方を疑って切り分けること。

### Phase 2：15.5秒テストの再構成（ゲート：Phase 1が全通過）

現状 `npm test` 18秒のうち15.5秒が `枝刈り…完全一致` 1本。§2.3のとおりこれは枝刈りしか検証していない。

- **このテストは消さない**（枝刈りの回帰検出という役割は本物。`optimizer.test.ts:193` のコメントにあるとおり、実際に不一致を検出した実績がある）。
- Phase 1のオラクルテストが `assignment.ts` をカバーするようになったので、**両者の役割分担をテストのコメントに明記する**こと。
- 実行時間が気になる場合のみ、`bruteForceOptimize` 側の候補数を減らす方向で調整する。**枝刈り側の検証を弱めないこと。**

### Phase 3（任意・別合意）：§2.2の潜在バグへの対応

内側に「全社売上>58億」を制約として入れた完全MILP定式化をオラクルとして書き、`runOptimization` 全体を検証する。実害が確認されていないため**本書では着手しない**。やる場合は別途合意を取ること。

## 7. やってはいけないこと

- `src/` 配下に `highs` を import すること。
- 数式・定数・アルゴリズムを変更すること（CLAUDE.md §9）。オラクルが不一致を出しても、**直す前に報告**。
- 割当（`Record<string, UnitId>`）そのものを期待値と比較すること。同値解があるため落ちる。
- 絶対誤差で浮動小数を比較すること。値のスケールは1e7。
- 既存の `枝刈り…完全一致` テストを削除・弱体化すること。
- WASM初期化をテストごとに行うこと。

## 8. 補足：課題2の答えを本当に左右しているもの

ソルバでは解決しない別のリスクとして記録しておく。

課題原文の計算仕様は **「コスト = 人件費 × 3」** のみで、`COST_UNIT_DIVISOR = 100` はチーム独自の単位解釈（CLAUDE.md §8）。課題2は利益最大化なので、この解釈が答えを直接決める。実測：

| 解釈 | 配分 | A利益 |
|---|---|---:|
| `÷100`（現行） | A:47 B:41 C:12 | **19.44** |
| `÷1`（課題原文の字面どおり） | A:40 B:35 C:25 | **-699.25** |

`÷1` だと全社コストが2,182億円に対し全社売上が約60億円となり、企業として成立しない。`÷100` が妥当という現行の判断を支持する材料はある。ただしこれは**課題原文に書かれていない解釈**であり、「課題2が正しいか」を最も強く左右しているのはアルゴリズムではなくこの1行である。製品カタログで明示しておくのが安全。
